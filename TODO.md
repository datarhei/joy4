# TODO: RTMP / E-RTMP v1 review findings

Scope: `format/rtmp`, `format/flv`, `format/flv/flvio`. One commit per finding.

## A. Critical: a remote client can crash the process or exhaust its memory (no `recover` anywhere)
1. [x] **Panic on a short HEVC ExHeader video message.** In `flvio.go:311-315`, `videoParseHeader` reads the 3-byte CTS (`pio.I24BE(b[n:])`) without a length check. A 5-byte video message `0x91 'h' 'v' 'c' '1'` panics with index-out-of-range. That kills the whole server, because `HandleNetConn` and `Serve` have no `recover`.
2. [x] **Unbounded allocation in an AMF0 strict array.** In `amf0.go:421-424`, `make(AMFArray, count)` uses an untrusted 32-bit count. A count of 0xFFFFFFFF in the `connect` command means about 64 GB, which ends in a fatal OOM before any authentication. The count must be capped by the remaining bytes.
3. [x] **Large pre-allocation per chunk stream.** `chunkStream.Start()` (`rtmp.go:403`) allocates `msgdatalen` (up to 16 MB) as soon as the header arrives. With 16 csids allowed, that is about 256 MB per connection right after the handshake, with nothing to limit it. Allocate gradually, or cap the message size, at least for non-A/V types and before `connect`.
4. [x] **Unbounded AMF0 recursion.** Deeply nested objects/arrays in a 16 MB message can hit Go's 1 GB stack limit, which is fatal. Add a depth limit.
5. [x] **No validation of SetChunkSize.** At `rtmp.go:1951`, 0 makes `readChunk` read 0-byte chunks forever and desync the stream. A value with the MSB set is negative on 32-bit, which panics on the slice. Clamp it to 1..0xFFFFFF and reject 0.
6. [x] **No default timeouts.** `ConnectionIdleTimeout` defaults to 0 on the server. The client has no deadline after dial (`DialTimeout` only covers TCP connect). Idle or slowloris peers can hold goroutines during the handshake and `readConnect` forever.

## B. Protocol correctness bugs (legacy RTMP)
7. [x] **Inconsistent extended timestamp at exactly 0xFFFFFF.** `fillChunkHeader` writes the extended field only when `ts > 0xFFFFFF` (`rtmp.go:1387/1399`, and `writeAVTag:1276`). `fillChunkHeader3` writes it when `ts >= 0xFFFFFF` (`:1436`). The reader (`:1529`) expects the extended field when the 24-bit value is `== 0xFFFFFF`. So at ts = 16777215 ms (about 4h39m) the type 0 header has no extended field but the type 3 chunks do, and the stream is corrupted. Use `>=` everywhere.
8. [x] **Ack sequence number is wrong.** `pollMsg` sends `conn.ackn` and then sets it to 0 (`:500-506`). The spec says the sequence number is the total number of bytes received so far (mod 2^32). Peers that do real windowing (FMS/Wowza-style) will see acks that never move forward. Use the running total (`txrxcount.rxbytes` already has it, but it also needs the handshake bytes).
9. [x] **Server simple handshake sends S2 = zeros.** In `handshakeServer` (`:2137-2139`), `copy(S2, C2)` runs before C2 has been read, so S2 is all zeros. S2 must echo C1. Also, S1 is a copy of C1 rather than the server's own time and random bytes. Clients that verify S2 (librtmp warns) see a mismatch.
10. [x] **Client handshake.** C1 is all zeros (`hsCreate01` is commented out), and S0's version is not checked. The `if ver != 0` branch is dead code, because C2 = S1 either way, so a complex-handshake response is never computed. Some strict servers or CDNs may reject this.
    - The complex (digest) handshake is still not implemented in the client (the simple handshake is fixed). Not required for now (decided 2026-11-02): all common servers and ingests (YouTube, Twitch, Facebook, nginx-rtmp, SRS, Wowza, Red5, AMS) accept the simple handshake, which OBS (librtmp) uses as well. The complex handshake is only needed for RTMPE (obsolete, replaced by RTMPS, see #28) and SWF verification, both Flash-era features. If needed, the client could reuse the digest code of the server handshake.
11. [x] **AMF messages are never split into chunks.** `writeAMF0Msg` writes the whole message as one chunk, whatever `writeMaxChunkSize` is. Today this is hidden by the 64 KB chunk size, but metadata over 64 KB (user-supplied via `SetMetaData`) desyncs the peer. It should reuse the chunking loop from `writeAVTag`.
12. [x] **Messages over 16 MB are not checked.** `PutU24BE` silently truncates the length in `fillChunkHeader`.
13. [x] **Type 3 continuation with extended timestamp.** At `:1670-1680`, the code peeks 4 bytes and guesses whether they are the extended timestamp. If the payload happens to start with those bytes, it desyncs. It also reads into bufio's own peek buffer (use `Discard(4)`), and those 4 bytes are not added to `n`, so the ack count is low.
14. [x] **Unhandled control messages.** Abort (2) is not handled; it should drop the partial message on that csid. SetPeerBandwidth (6) is not answered with a WindowAckSize.
15. [x] **Fixed limit of 16 chunk streams** (`readChunk`). A reasonable DoS guard, but hard-coded, and the new chunk stream was added before the check. The limit counts different chunk stream ids in use, not how high they are (FFmpeg, OBS and joy4 use about 3–8). Make it configurable and document it.
16. [x] **Type 3 starting a new message after type 0** keeps the same absolute timestamp (delta 0). FFmpeg/SRS add the previous timestamp field as the delta instead. This interop gap feeds the "same timestamp" heuristic in #18.

## C. Timestamp handling
17. [x] **Drift on non-monotonic timestamps.** At `:1754-1762`, a backward step is ignored and the next forward step adds the full delta, so `xtimenow` drifts ahead. This hits encoders that mux audio and video on one csid, or that jitter. On wraparound, it adds `timenow` but loses `(max - prev)`.
18. [x] **"Same timestamp" heuristic.** More than 10 equal or backward timestamps among the first 20 messages switch that csid to wall-clock time. This is per csid, so audio can be on wall clock while video keeps encoder time, which desyncs A/V, and the wall clock starts at connect time rather than at the stream's timestamp. After 20 messages, the same pattern drops the whole connection with an error.
19. [x] **Writer wraps at 2^31.** `writeAVTag` masks `ts & 0x7FFFFFFF`, while RTMP timestamps are 32-bit. Readers that unwrap at 2^32 jump after about 24.8 days.

## D. Command / session layer
20. [x] **`OnPlayOrPublish` gets no stream info.** It receives only the command name and the connect params, and it runs before `conn.URL` is set (`:686` vs `:716`), so it cannot check the stream key. On rejection, the server still sends **`NetStream.Publish.Start`** and then closes. It should send `NetStream.Publish.BadName` or `Unauthorized` with level `error`.
21. [x] **No authorization hook for `play`.** `OnPlayOrPublish` is never called in the play branch.
22. [x] **`objectEncoding` default is wrong.** It defaults to **3** when the client didn't send it (`:625-628`). The server only speaks AMF0, so it should be 0. AMF3 command messages (type 17) are parsed as AMF0 after skipping one byte, so any real AMF3 value (`0x11` avmplus marker) fails. AMF3 data messages (type 15) are ignored.
    - AMF3 values in command messages (type 17) and data messages (type 15) are still not supported. Not required for now (decided 2026-11-02): FFmpeg and OBS send AMF0 only.
23. [x] **`onStatus` transaction id.** It uses the request's transid; the spec says 0. The publish `type` argument is ignored (fine). `releaseStream`, `FCPublish`, `FCUnpublish`, `deleteStream`, `closeStream` and `getStreamLength` get no reply. Some clients wait for `onFCPublish`.
24. [x] **Commands are ignored after setup.** Once the stream is publishing or playing, commands are dropped (`pollAVTag`). `deleteStream` / `FCUnpublish` from a publisher don't end the stream; only TCP EOF does. In server play mode nobody reads from the socket, so pause, seek and closeStream from players are never seen.
    - [x] During playback nobody reads from the socket of the player, so closeStream, deleteStream, pause, acks and ping responses of players are never seen. Needs a read loop alongside WritePacket, see #43.
25. [x] **Client does not handle errors.** `_error` replies to connect or createStream are ignored, so it loops until the peer closes. Transaction ids are not matched. The client doesn't wait for `NetStream.Publish.Start` or `Play.Start`, and it never surfaces `onStatus` errors (BadName, StreamNotFound, UnpublishNotify).
26. [x] **Client publishing never reads.** Server pings are never answered and server acks and onStatus messages pile up. Some servers drop clients that don't answer pings.
27. [x] **Client details.** It sends SetPeerBandwidth (normally server-to-client only). SetBufferLength goes to msgsid 0 before the stream exists, so it has no effect. `publish` has no `"live"` argument, and `releaseStream`/`FCPublish` are not sent, which some CDNs require.
28. [x] **No RTMPS on the client side.** `Dial` is TCP only, and `ParseURL` always defaults to port 1935, with no `rtmps://` or port 443 handling. The server does have TLS.

## E. Enhanced RTMP v1 / FLV layer
29. [x] **VVC is broken on ingest.** In `flv.go:152-193`, the VVC branch was nested *inside* the `FOURCC_AV1` branch by commit 8b2ed73. Its sequence header is never parsed, so the stream never probes, and VVC frames are emitted with a stale or zero stream index.
30. [x] **VVC composition time is missing.** VVC `CodedFrames` carries no CTS in parse or fill (only HEVC does, `flvio.go:311,335`). E-RTMP v2, which defines vvc1, says CodedFrames for vvc1 (like avc1 and hvc1) has an SI24 CTS. This breaks interop and loses PTS for B-frames. Either add the CTS or always send `CodedFramesX`. Also, `vvc1` is not in the client's `fourCcList` (`rtmp.go:855`).
31. [x] **Negative composition time is corrupted on write.** `int32(CompositionTime & 0x7FFFFF)` (`flvio.go:337,347`) clears the sign bit, so −33 is written as +8388575. Use `& 0xFFFFFF`, or pass the int32 straight through.
32. [x] **Packets get the wrong stream index.** `TagToPacket` ignores FourCC/CodecID and always sets `Idx = VideoStreamIdx`/`AudioStreamIdx`, which defaults to 0, even when no stream of that kind was probed. Video data can end up on the audio stream (unsupported FourCC, legacy VP6/H.263, or no sequence header). `CacheTag` sets the index when the packet is cached, so frames that arrive before their sequence header get the wrong index.
33. [x] **Legacy CodecID is not checked.** Every non-ExHeader video is treated as AVC (`flvio.go:276`), so H.263, VP6 and Screen Video are parsed and emitted as H.264.
34. [x] **ExHeader `PacketTypeMetadata` (HDR colorInfo) is dropped.** For metadata the frame type is to be ignored (E-RTMP v1 doesn't mask it with 0b0111 for this packet type), so it keeps the 0x8 bit and the packet is filtered out in `handleMsg` with the non-video frame types. The colorInfo is now parsed (`flvio.ParseColorInfo`), and it's available with `GetColorInfo` for the video packet read last (`rtmp.Conn`, `flv.Demuxer`, also while probing). `SetColorInfo` writes it before the next video packet (`rtmp.Conn`, `flv.Muxer`, HEVC/AV1/VP9/VVC only). `SequenceEnd` is dropped on purpose. An ExHeader command frame (E-RTMP v2) has no FourCC; it closed the connection with a parse error and is now skipped.
35. [x] **Mid-stream sequence headers are dropped.** After probing, a new `SequenceStart` or `AVC_SEQHDR` (resolution or codec change, re-sent config) is discarded, and there is no way to signal new codec data downstream. Fixed for H.264 and HEVC with in-band parameter sets (`flv.Prober`, so for the RTMP server/client and the FLV demuxer): a sequence header that differs from the current config is parsed, and its SPS and PPS (HEVC: VPS, SPS and PPS) are put, length-prefixed, in front of every following key frame, so a reader that joins later also gets them. A re-sent, identical config is ignored, and a change back to the config of the stream stops the insertion. A second sequence header during probing is cached and applies to the frames after it. Ignored as before: an invalid record, a different NALU length size, a codec change, and new configs of VP9 (not needed), AV1, VVC and AAC. `Streams()` and the metadata keep the first config (e.g. its width and height). Also fixed: `hevcparser` read `lengthSizeMinusOne` of the hvcC from byte 4 (as in the avcC) instead of byte 21, which gives 1 instead of 4 for FFmpeg's records. FFmpeg with a stream that changes from 320x240 to 640x360 (H.264 and HEVC): remuxed by joy4, the decoded frames are identical to the source, and through the joy4 relay (rtmp_server_channels) a player from the start and a player that joins after the change decode the new size without errors. Before, FFmpeg decoded the second part with the old config (errors, or 320x240).
    - [ ] Option B: an explicit change signal for new codec data, e.g. `GetCodecData(idx)` on `rtmp.Conn` and `flv.Demuxer` (the config of the packet read last) and `SetCodecData(idx, codecData)` on the muxers (sends a new sequence header). It would be needed for AAC config changes, the exact new width and height, and AV1/VVC. Only code that uses it would benefit, e.g. core and `pubsub` would have to pass it on.
36. [x] **Server doesn't confirm E-RTMP support.** The `connect` reply doesn't echo `fourCcList`, and the client's `fourCcList` is ignored. Not strictly required by v1, but a capability response helps clients decide. A client that announces E-RTMP (`fourCcList` or `videoFourCcInfoMap`) now gets the supported video codecs in the `_result` properties (`fourCcList`, and `videoFourCcInfoMap` with CanForward, as E-RTMP v2 recommends); the reply to legacy clients is unchanged. `Conn.ConnectParams()` gives the handlers the command object of `connect`. The client also announces `vvc1` (missing since #30) and sends `videoFourCcInfoMap`.
37. [x] **Prober details.** Speex/Nellymoser frames after the first one, during probing, are dropped. Metadata `audiocodecid`/`videocodecid` turn on HasAudio/HasVideo even for unsupported codecs, which costs 20 packets of probe latency. A failing PushTag is only logged. Nellymoser is always probed as 16 kHz: the SoundRate of SoundFormat 6 is ignored, SoundFormat 4 (16 kHz mono) and 5 (8 kHz mono) are not recognized, and `PacketToTag` writes SoundRate 0 (5.5 kHz) for Nellymoser. Fixed: Speex and Nellymoser frames are cached for every tag during probing, not only the first one. The onMetaData codec ids enable HasVideo/HasAudio only for supported codecs (new `Prober.PushMetadata`): videocodecid 7 or the FourCC of hvc1/vp09/av01/vvc1 as a number or a string ("avc1" etc.), audiocodecid 10, 11, 4, 5, 6 or "mp4a". With H.263 video and AAC audio from FFmpeg, probing ends after 2 ms instead of 1.5 s (20 packets). The prober keeps the last error of `PushTag` (`Prober.Err`): invalid tags are still skipped, but if probing ends without any stream, `Streams()`/`ReadPacket()` return that error ("rtmp: no stream probed: ...") instead of an empty stream list. Nellymoser: SoundFormat 4 (16 kHz mono) and 5 (8 kHz mono) are recognized, the sample rate of SoundFormat 6 is taken from SoundRate, and `PacketToTag`/`NewMetadataByStreams` write the SoundFormat and SoundRate as FFmpeg does (16 kHz: 4, 8 kHz: 5, otherwise 6 with SoundRate). Before, FFmpeg Nellymoser with 8 or 16 kHz was not probed at all, and the other rates came out as 5512 Hz. Not changed: the FLV file demuxer still takes HasAudio/HasVideo from the flags of the file header, not from onMetaData.
    - [x] `rtmp.probe` assigns the error of `PushTag` to its named return value. If the `PushTag` that completes probing fails (e.g. the last one before the probe limit), `probe` returns that error and the connection fails, although the error should only be logged. Seen with H.263 (`flv1`) from FFmpeg, whose frames are parsed as H.264 (#33).
38. [x] **Inconsistent codec support.** `NewMetadataByStreams` rejects NELLYMOSER, while `CodecDataToTag` and `PacketToTag` support it. AAC with more than 2 channels is flagged mono. Neither is harmful, but it's inconsistent. Fixed: `NewMetadataByStreams` writes `audiocodecid` 6 for Nellymoser. The prober created the Nellymoser stream as a `fake.CodecData`, which has no `PacketDuration` and therefore isn't an `av.AudioCodecData`, so the type assertion in `NewMetadataByStreams` (and e.g. in `av/transcode`) panicked; there is now a `codec.NellymoserCodecData` like `codec.SpeexCodecData` (256 samples per 64-byte block, as in FFmpeg). AAC tags are always written with 44 kHz, 16 bit and stereo (0xAF), as the FLV spec requires and FFmpeg does; the actual sample rate and channels are in the AudioSpecificConfig. Mono AAC was written as 0xAE before. Mono and 5.1 AAC from FFmpeg, remuxed by joy4, are read back by ffprobe with the right channels.
50. [ ] **Legacy video codecs are not supported (optional, for later).** The FLV spec defines the video codec ids 2 (Sorenson H.263), 3 (Screen video), 4 (On2 VP6), 5 (On2 VP6 with alpha) and 6 (Screen video v2), but joy4 only supports AVC (7) in the legacy header. Since #33, such streams are probed without video. Support would need a codec type in `av` and `CodecData` without configuration record (width and height from the picture header), probing from the first frame (like Speex/Nellymoser), writing them in `CodecDataToTag`/`PacketToTag`/`NewMetadataByStreams`, and accepting the disposable inter frame (3) of H.263 in `handleMsg`.

## F. AMF0
39. [x] **Strings of exactly 65536 bytes are encoded wrongly.** The check is `<= 65536` (`amf0.go:126,199`), so the uint16 length overflows to 0. It should be `<= 65535`.
40. [x] **Unsupported Go types encode to 0 bytes silently.** For example `map[string]interface{}`, `[]interface{}`, pointers. Inside an AMFMap, the key is then written with no value, which corrupts the message. That is reachable through `SetMetaData`. Return an error or panic.
41. [x] **Unsupported markers.** Reference, typed-object and AMF3-switch markers fail the whole message. A metadata parse error kills the connection.
    - References (0x07) are still not supported, they need the parser to keep track of the parsed objects. AMF3 (0x11) see #22. Not required for now (decided 2026-11-02): FFmpeg, OBS (librtmp) and hardware encoders never write references, and FFmpeg, librtmp and nginx-rtmp can't parse them either. They would only come from Flash/AIR clients or Red5/FMS server-side code passing complex objects. A reference in a data message drops that message, in a command message it fails the connection.

## G. Concurrency / lifecycle / API
42. [x] **Data race on the byte counters.** `TxBytes`/`RxBytes` are read from other goroutines without atomics.
43. [x] **`Conn` is not safe for concurrent reads and writes.** The read path writes Acks and Ping responses through the shared `bufw` and `writebuf`. Any user who reads and writes at the same time (needed to fix #24/#26) will corrupt output. A write mutex is needed. This is also needed for reading from the socket of a player during playback (#24).
44. [x] **Unsynchronized server shutdown.** `Server.Close` races with `Serve` on `listener`/`doneChan`, and calling `Close` twice can panic. Active connections are not closed.
45. [x] **Leaking `Handler` helpers.** `ServerMuxer` and `ServerDemuxer` leak the server, and they block forever on unbuffered channels for a second client or when `ListenAndServe` returns. They now serve exactly one client: the listener is closed after the first client, further clients are rejected, listen errors are returned, and closing the returned connection ends everything.
46. [x] **Minor:**
   - `writeAVTag` flushes after every frame, which is one syscall per frame. Kept on purpose: it gives the lowest latency for a live stream, batching would only help when many packets are written back-to-back. Documented in the code.
   - The error is logged twice (`HandleNetConn` and `Serve`). Fixed: only `HandleNetConn` logs it.
   - `writeConnect` duplicates the WindowAckSize handling. Already gone since #25: `writeConnect` waits with `waitResult`, which leaves the WindowAckSize to `handleMsg`.
   - `writeAVTag` gives csid 0 to non-A/V tags. Fixed: it returns an error for other tag types (not reachable through `WriteHeader`/`WritePacket`).
   - `SplitPath` puts everything after the first segment into the stream name (`app/instance` ambiguity). Kept as the default (documented in `SplitPath`). New `DialOptions.App` sets an application name with more than one segment, like FFmpeg's `-rtmp_app`; the path of the URL must start with it, the rest is the stream name. FFmpeg in listen mode with rtmp://host/live/inst/test warns "App field don't match up: live <-> live/inst" for the default and accepts the connect with `App: "live/inst"`.
   - There are no unit tests in `format/rtmp`. Done along the way of the other findings.
48. [x] **Publishing client doesn't end the stream on Close.** `Conn.Close` of a publishing client only closes the TCP connection, without sending `FCUnpublish` and `deleteStream` first as FFmpeg and OBS do. A server that reacts to these commands (e.g. joy4 since #24) sees a broken connection instead of the end of the stream. (FFmpeg as receiver with `-listen 1` reports "Error during demuxing: Input/output error" for every publisher, also for FFmpeg itself, as it doesn't handle these commands in listen mode.)
49. [x] **Broken examples.** Two examples don't compile: `examples/rtmp_publish` calls `rtmp.Dial` without the `DialOptions` argument (added in 09a60de), and `examples/rtmp_server_channels` subtracts an `int64` (`pkt.Time`) from a `time.Duration`. Fixed: `rtmp_publish` passes `rtmp.DialOptions{}`, and `rtmp_server_channels` keeps the last packet time as `int64` and converts the difference from milliseconds to a `time.Duration`. The expired `examples/rtmp_server/cert.pem` (January 2022, no subject alternative names) turned out to be a local file only: `*.pem` is in `examples/rtmp_server/.gitignore` and was never committed, so there is nothing to change in the repository.

## H. Other packages
47. [x] **`pktque.Walltime` never paces packets.** `av/pktque/filters.go`: `ModifyPacket` sets the start time only if `firsttime == math.MinInt64`, but the zero value of `firsttime` is 0, so the start time is never set and the filter never sleeps. A publisher using it (e.g. `examples/rtmp_publish`) sends a whole file at once instead of in real time. It also uses `time.Now().Unix() * 1000`, which has only second resolution. Fixed: the start is set by the first packet (with a `started` flag), the pacing is relative to the time of the first packet (a stream that doesn't start at 0 is not delayed by that offset) and uses `time.Since` (monotonic, ms resolution). All packets are paced, not only those of stream 0. A 5 s file is now published in 5.35 s instead of 0.27 s.
51. [x] **`h264parser` uses a fixed crop unit.** `codec/h264parser/parser.go` computes the width and height from the SPS with `CropLeft*2`, `CropTop*2` etc., i.e. a crop unit of 2, which is only correct for 4:2:0 chroma with frame_mbs_only_flag = 1. The crop unit depends on chroma_format_idc (4:2:0: 2x2, 4:2:2: 2x1, 4:4:4 and monochrome: 1x1) and, vertically, on frame_mbs_only_flag (ISO/IEC 14496-10, 7.4.2.1.1). Seen with a 640x360 4:4:4 stream from FFmpeg (libx264), for which joy4 reports 640x352 (e.g. in the metadata). Fixed with the crop unit from the spec. This also fixes interlaced 4:2:0 (640x372 instead of 640x360). Two more SPS parsing bugs that change the size: 4:4:4 has 12 scaling lists instead of 8, and the profiles 128, 138, 139, 134 and 135 (MVC, SVC) also have the chroma format fields.
52. [ ] **`go vet ./...` fails outside RTMP.** Already before this branch, so `go vet ./...` and `go test ./...` can't be used for the whole module:
   - `format/rtsp/sdp/parser_test.go` calls `Decode`, which doesn't exist (the parser has `Parse`), so the test doesn't compile.
   - `utils/bits/bits_test.go` calls `PutUInt64BE`, which doesn't exist (there is `pio.PutU64BE` with a different signature), so the test doesn't compile.
   - `utils/bits/pio/vec_test.go`: the example `ExampleVec` refers to the unknown identifier `Vec` (vet "tests" check; the functions are `VecLen`, `VecSlice`, `VecSliceTo`).
   - `format/mp4/mp4io/gen/pattern.go` is the input pattern of the code generator (`gen.go`) with undefined identifiers such as `atom` and `MovieHeader`. It is part of the package `main` without a build constraint, so the package doesn't build. A `//go:build ignore` tag (or a move out of the package) would exclude it.
   - `format/rtsp/client.go`: unreachable code at lines 450, 505, 553, 565 and 1220 (vet warnings, not build errors).
53. [x] **`hevcparser` reads and writes the HEVCDecoderConfigurationRecord header at wrong offsets.** `codec/hevcparser/parser.go`, ISO/IEC 14496-15, 8.3.3.1. FFmpeg ignores these fields when decoding, so it has no visible effect so far (found while working on #35). Fixed: `Unmarshal` reads all header fields at the offsets of the spec (new fields in `HEVCDecoderConfRecord`, e.g. `GeneralProfileIDC`, `GeneralLevelIDC`, `ChromaFormatIDC`, `BitDepthLumaMinus8`; `HEVCProfileIndication`, `ProfileCompatibility` and `HEVCLevelIndication` are kept and have the values of byte 1, byte 2 and the level), and walks all `numOfArrays` arrays by their NAL unit type, skipping other types such as SEI. `Marshal` writes the header from these fields, with the reserved bits set to 1, and writes only non-empty arrays; `Len` is right for arrays with more than one NAL unit. `NewCodecDataFromVPSAndSPSAndPPS` takes the fields from the SPS. For that, `ParseSPS` now fills `ProfileIdc` and `LevelIdc` (they were never set), and the new `ChromaFormatIdc`, `BitDepthLumaMinus8`, `BitDepthChromaMinus8`, `MaxSubLayersMinus1` and `TemporalIdNestingFlag`; the general compatibility and constraint flags were always 0, because they were ANDed into zero values. A record built from FFmpeg's VPS, SPS and PPS (Main, Main 10 and RExt 4:4:4) now has the same header as FFmpeg's own record, apart from the number of arrays (FFmpeg adds an SEI array); before, the level, chroma format, bit depth, temporal layers and reserved bits were 0.
    - `Marshal` (used by `NewCodecDataFromVPSAndSPSAndPPS`, which joy4 itself doesn't call) writes the profile byte, the first compatibility byte and the level to bytes 1, 2 and 3, taken from `sps[3]`, `sps[4]` and `sps[5]`. The level belongs in byte 12, and in the SPS it is at offset 14 of the RBSP, i.e. after removing the emulation prevention bytes (after the NAL header, the sub-layer byte, 4 bytes of compatibility flags and 6 bytes of constraint flags). The other compatibility and constraint flags are missing, and bytes 13 to 20 stay 0: the reserved bits that must be 1, and chroma_format_idc 0 (monochrome) and bit depth 8 instead of the values from the SPS. The level in the record is therefore always 0.
    - `Unmarshal` reads `HEVCProfileIndication`, `ProfileCompatibility` and `HEVCLevelIndication` from bytes 1, 2 and 3; the level is in byte 12. It ignores `numOfArrays` and the NAL unit type of the arrays and expects exactly a VPS, an SPS and a PPS array in this order; other orders or an SEI array before them break the parsing. The count of the VPS array is read from the low 5 bits of its low byte only.

## I. E-RTMP v2: extended audio, new audio codecs, multitrack

Reference: [enhanced-rtmp-v2](https://github.com/veovera/enhanced-rtmp/blob/main/docs/enhanced/enhanced-rtmp-v2.md), sections Enhanced Audio, Enhanced Video, Multitrack Streaming, Enhancing NetConnection connect Command. Interop partner: FFmpeg 9.0.1 writes and reads all of it. Additional tracks are written as Multitrack/OneTrack messages (video `0x96 00 'avc1' <trackId>`, audio `0x95 00 'mp4a' <trackId>`), track 0 as before. Opus, FLAC, AC-3 and E-AC-3 are written with the ExAudioTagHeader (SequenceStart `0x90`, MultichannelConfig `0x94`, CodedFrames `0x91`), MP3 with the legacy header (SoundFormat 2).

Decisions:
- Decided: all tracks are passed on by default, i.e. the demuxers return a stream per track. Which tracks an RTMP player gets is negotiated (#59).
- Decided: audio multitrack comes together with video multitrack, so #54 and #55 come before #57.

54. [x] **ModEx is not supported.** A video or audio packet with `PacketType` ModEx (7) and its `VideoPacketModExType`/`AudioPacketModExType` (e.g. TimestampOffsetNano) can't be parsed. Parse and skip the ModEx data (size UI8+1, or UI16+1 if 256), keep the nano offset in the tag, and read the actual packet type after it. Writing isn't needed. Fixed for video: `flvio` parses any number of ModEx blocks (`PKTTYPE_MODEX`) before the actual packet type, with the 8 and 16 bit sizes, keeps the TimestampOffsetNano in `Tag.TimestampNanoOffset` and skips other ModEx types. The offset is not applied to the packet (`av.Packet.Time` has ms resolution) and not written. Audio ModEx comes with #55, because it only exists in the ExAudioTagHeader. An FFmpeg HEVC FLV with a TimestampOffsetNano inserted in front of every video tag (FFmpeg itself reads it) is remuxed by joy4 with identical decoded frames; before, joy4 found no video in it.
55. [ ] **The ExAudioTagHeader is not supported.** joy4 only knows the legacy AudioTagHeader. Parse and write SoundFormat 9 (ExHeader) with AudioPacketType (SequenceStart, CodedFrames, SequenceEnd, MultichannelConfig, Multitrack, ModEx) and the audio FourCC (`mp4a`, `Opus`, `fLaC`, `ac-3`, `ec-3`, `.mp3`). AAC via `mp4a` maps to the existing AAC stream. MultichannelConfig (channel order, count, mapping or flags) is parsed and kept in the tag; it is needed for Opus without an ID header. Unknown FourCCs are skipped in a controlled way. Probing, `TagToPacket`, `CodecDataToTag`, `PacketToTag` and the metadata (`audiocodecid` as FourCC) handle it, and the server announces the audio codecs in `audioFourCcInfoMap` in the connect result (like `videoFourCcInfoMap`, #36).
56. [ ] **The new audio codecs of E-RTMP v2 are not supported.** `av` has no codec types for them. Each needs a codec type, a `CodecData` with sample rate, channel layout and `PacketDuration`, and the mapping in `format/flv` (#55). One commit per codec:
    - [ ] **Opus** (`Opus`): the SequenceStart is the ID header (`OpusHead`, RFC 7845 5.1) with channels, pre-skip and channel mapping, or empty (then MultichannelConfig or mono/stereo). Always 48 kHz. The duration from the TOC byte (RFC 6716 3.1).
    - [ ] **FLAC** (`fLaC`): the SequenceStart is `fLaC` and the STREAMINFO block (sample rate, channels, bits per sample). The duration from the block size in the frame header.
    - [ ] **AC-3** (`ac-3`) and **E-AC-3** (`ec-3`): no config in the SequenceStart, sample rate and channels come from the first syncframe (probing from the first frame, like Speex). 1536 samples per AC-3 frame, E-AC-3 from numblkscod.
    - [ ] **MP3** (`.mp3`, and legacy SoundFormat 2, which joy4 doesn't support either): sample rate and channels from the first frame header, 1152 or 576 samples per frame.
57. [ ] **Multitrack is not supported.** A video or audio message with `PacketType` Multitrack (video 6, audio 5) carries one track (OneTrack), several tracks with one codec (ManyTracks) or several tracks with their own codecs (ManyTracksManyCodecs), each with a trackId (UI8) and, except for OneTrack, its size (UI24). `flvio.Tag` can only describe one track. Add `TrackID` and a multitrack flag to `flvio.Tag`, split a message into one tag per track (e.g. `flvio.ParseTracks`), and let the RTMP read path and the FLV demuxer process all of them. Writing: track 0 without multitrack (as today), every other track as OneTrack, as FFmpeg does. ManyTracks batches are only parsed.
58. [ ] **The prober knows only one video and one audio stream.** Map (media type, trackId) to a stream index instead of `VideoStreamIdx`/`AudioStreamIdx`. Probing ends when every announced track has its config: the default tracks from onMetaData, the others from `videoTrackIdInfoMap`/`audioTrackIdInfoMap`, otherwise after `MaxProbePacketCount` as today. A track that appears after probing is dropped, because `Streams()` is fixed. The in-band parameter sets (#35) and the color info (#34) are kept per track. Writing: the n-th video or audio stream becomes trackId n, `NewMetadataByStreams` writes `videoTrackIdInfoMap`/`audioTrackIdInfoMap` for the tracks from 1 on.
59. [ ] **The Multitrack capability is not negotiated.** The server doesn't send `capsEx` with Multitrack (0x02) in the connect result, and the client doesn't announce it. A player that didn't announce Multitrack must only get track 0 of each media type, i.e. the first video and the first audio stream: its `Streams()` after `WriteHeader` only contains them, and the packets of the other streams are dropped. Otherwise it gets messages it can't parse. Note: FFmpeg 9.0.1 as RTMP player never announces `capsEx`, not even with `-rtmp_enhanced_codecs` (which only sends `fourCcList`), although its FLV demuxer reads multitrack. So the handler must be able to override the decision per connection before `WriteHeader` (e.g. `Conn.SetMultitrack(bool)`, set by core from a URL parameter or a configuration). The client announces Multitrack and `audioFourCcInfoMap`.
60. [ ] **Multitrack interop.** FFmpeg publishes 2 video and 2 audio tracks (different codecs and sizes) to the joy4 relay, FFmpeg players with and without multitrack read them back (all 4 streams, or only track 0), and an FLV file with multitrack is remuxed by joy4. The new audio codecs from FFmpeg (libopus, flac, ac3, eac3, libmp3lame) over RTMP and as FLV files. Optionally OBS multitrack video (Enhanced Broadcasting) against a custom server.
